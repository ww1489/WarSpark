# WarSpark 实施路线图

## 1. 文档目的

本文档将 WarSpark MVP 和后续版本拆成可执行阶段，明确每个阶段的目标、交付物、验收标准、主要风险和不做事项。

路线图基于：

- `docs/product/warspark-prd.md`
- `docs/product/mvp-scope.md`
- `docs/product/user-flows.md`
- `docs/product/page-spec.md`
- `docs/product/content-data-policy.md`
- `docs/architecture/data-model.md`

## 2. 总体策略

WarSpark 不从完整多端战争工具或公开社区阵型图库开始，而是先完成一个可验证闭环：

1. 用户可以输入部落 tag 或玩家 tag，读取官方战争数据。
2. 用户可以从战争目标或独立入口上传截图。
3. 系统可以自动处理截图并返回相似阵型、相关视频、防守回放和阵型链接。
4. 找阵结果可以沉淀为轻量阵型库。
5. 内部后台可以管理阵型、图片、链接、视频时间戳、审核和异常样本。

阶段顺序：

- Phase 0：产品文档和数据模型。
- Phase 1：基础数据模型、阵型库和内部后台骨架。
- Phase 2：官方战争 API、截图上传和自动找阵结果页。
- Phase 3：相关视频和防守回放关联。
- Phase 4：战争情报增强和复盘入口。
- Phase 5：复盘和资料沉淀。

## 3. Phase 0：产品文档和数据模型

目标：

- 在开发前锁定 MVP 边界、流程、页面、数据来源和核心数据模型。

交付物：

- MVP 范围文档。
- 用户流程文档。
- 页面规格文档。
- 内容与数据边界文档。
- 数据模型文档。
- 实施路线图。

验收标准：

- 所有 P0 文档状态为已完成。
- `documentation-status.md` 与实际文件一致。
- 文档中不存在未决占位词。
- MVP 边界明确排除用户注册、收藏、付费、多端 App、完整视频帧索引、自动配兵识别、AI 打法推荐。

主要风险：

- 继续扩大 MVP 范围。
- 页面规格和数据模型不一致。

风险控制：

- 新需求先对照 `mvp-scope.md`。
- 页面新增字段先对照 `data-model.md`。

不做事项：

- 不开始写业务代码。
- 不设计公开社区运营后台。
- 不写 P1 文档。

## 4. Phase 1：基础数据模型、阵型库和内部后台骨架

目标：

- 先建立可浏览、可管理的阵型资产基础，支撑后续找阵结果页和自动化入库。

交付物：

- 阵型库列表页。
- 阵型详情页。
- 基础阵型数据模型落地。
- 阵型图片、阵型链接、来源、审核状态、质量状态字段落地。
- 内部 admin API 骨架。
- 后端管理页面骨架。
- 自动化入库草稿和后台复核状态。

核心能力：

- 按 TH、类型、风格、来源、审核状态筛选阵型。
- 查看阵型图片。
- 打开或复制阵型链接。
- 展示链接状态：可用、失效、未验证、暂无。
- 展示质量状态：高可信、可参考、低可信、未知。
- 后台查看、编辑、隐藏、审核阵型。
- 后台管理 `official_open_layout`、`source_page`、`backup` 链接。

验收标准：

- 阵型库列表可以展示样本阵型。
- 阵型详情可以展示图片、TH、类型、来源、状态和阵型链接。
- 管理后台可以登录后查看和编辑阵型、图片、链接、审核状态。
- 失效链接不能被复制或打开。
- 待审核或低可信阵型有明确标记。

主要风险：

- 样本数据来源不清。
- 阵型链接和图片不匹配。
- 阵型库被做成公开社区运营系统。

风险控制：

- 所有样本数据必须记录来源。
- 低可信和待审核状态前端可见。
- MVP 只做轻量列表、详情和内部管理，不做用户投稿、收藏、评论、付费。

不做事项：

- 不做用户投稿审核。
- 不做 SEO 内容运营。

## 5. Phase 2：官方战争 API、截图上传和自动找阵结果页

目标：

- 用户可以从战争目标或独立入口上传截图，并看到一次完整的自动找阵结果。

交付物：

- 找阵页。
- 作战台 tag 查询。
- 战争情报页基础版。
- 官方 CoC API Client。
- 当前战争和 CWL 基础数据接入。
- 上传任务创建和状态展示。
- 找阵结果页。
- 找阵任务和结果数据模型落地。
- 低置信度、无结果、失败状态。

核心能力：

- 输入部落 tag 或玩家 tag。
- 展示当前战争、CWL 基础结构、TH 分布、成员、攻击次数、星数和摧毁率。
- 从敌方目标进入找阵。
- 上传阵型截图。
- 创建找阵任务。
- 自动校验图片类型、大小、尺寸、EXIF 和频率限制。
- 自动识别 TH、判断截图质量、执行候选匹配。
- 展示处理状态。
- 展示识别 TH、截图质量和候选数量。
- 展示相似阵型候选。
- 从相似阵型进入阵型详情。
- 支持重新上传。

验收标准：

- 用户能从首页进入找阵页。
- 用户能从战争情报页选择目标进入找阵。
- 用户能完成上传到结果页的完整流程。
- 成功结果展示相似阵型。
- 低置信度结果明确提示。
- 无结果时展示重新上传、同 TH 热门视频或反馈入口。
- 失败时展示失败原因和重新上传入口。
- 匿名上传只允许 jpg/jpeg/png/webp，单图最大 10MB，按 IP 限流。

主要风险：

- 找阵算法不成熟导致体验不可用。
- 低置信度结果误导用户。
- 官方 API 缓存和权限导致战争数据不完整。
- 上传接口被匿名滥用。

风险控制：

- MVP 优先使用自动候选匹配，不承诺 100% 精确 AI。
- 低可信结果必须标记。
- 找阵流程必须能独立运行。
- 官方 API 不可用时，找阵流程仍可独立使用。
- 上传限制和 IP 频控必须上线。

不做事项：

- 不做复杂图片编辑器。
- 不做批量上传。
- 不做大规模视频帧索引。
- 不做自动识别配兵或打法。

## 6. Phase 3：相关视频和防守回放关联

目标：

- 找阵结果页可以提供可学习的视频参考和防守回放。

交付物：

- 视频基础数据模型落地。
- 阵型和视频关联模型落地。
- 进攻视频分组。
- 防守回放分组。
- YouTube 时间戳跳转。
- 视频关联类型：精确关联、相似参考、同 TH 参考。

核心能力：

- 展示视频标题、频道、星数、摧毁率、时间戳、标签。
- 区分进攻视频和防守回放。
- 打开 YouTube 对应时间戳。
- 在阵型详情页展示关联视频。
- 无视频时展示空状态。

验收标准：

- 找阵结果页可以展示进攻视频和防守回放两个分组。
- 视频卡片可以打开正确时间戳。
- 相似参考和同 TH 参考不能展示为精确关联。
- 没有关联视频时，页面仍可展示相似阵型和阵型链接。

主要风险：

- 视频关联质量不稳定。
- 用户误以为视频是系统推荐打法。
- YouTube 链接失效。

风险控制：

- 使用“相关视频”“视频参考”文案。
- 记录关联类型和审核状态。
- 失效视频展示不可访问状态。

不做事项：

- 不下载 YouTube 视频。
- 不自动解析视频画面。
- 不自动提取配兵链接。
- 不做 AI 总结打法。

## 7. Phase 4：战争情报增强和复盘入口

目标：

- 在首轮官方 API 接入基础上增强战争情报体验，并为复盘沉淀做入口。

交付物：

- 历史战争查询或缓存快照浏览。
- 更完整的 CWL 轮次视图。
- 目标筛选和风险排序。
- 战争快照复盘入口。
- 后台刷新、缓存和错误状态管理。

核心能力：

- 查看历史快照。
- 对 CWL 轮次做基础筛选。
- 按 TH、剩余攻击、被打结果筛选敌方目标。
- 从战争结果进入复盘草稿。
- 管理官方 API 缓存刷新。

验收标准：

- 用户可以查看已缓存的战争快照。
- 用户可以从战争快照进入复盘草稿。
- 官方 API 不可用时，已有快照和找阵流程仍可使用。
- 无法刷新战争数据时有明确错误状态。

主要风险：

- 战争数据范围扩张为完整 War Report。
- 找阵流程被战争数据耦合。
- 历史战争需求过早扩大。

风险控制：

- 战争数据增强仍服务目标上下文、找阵和复盘。
- MVP 找阵流程保持独立。
- 完整 War Report 式多端工具不进入本阶段。

不做事项：

- 不做完整 War Report。
- 不做多账号同步。
- 不做推送提醒。
- 不做复杂历史战争分析。

## 8. Phase 5：复盘和资料沉淀

目标：

- 战后数据反哺阵型库、视频资料库和后续找阵排序。

交付物：

- 复盘页基础版。
- 攻击记录展示。
- 防守记录展示。
- 阵型表现统计。
- 攻击结果表现统计。
- 关键阵型和关键视频标记。

核心能力：

- 查看战争结果。
- 查看攻击记录和防守记录。
- 关联阵型详情。
- 关联视频时间戳。
- 将复盘结果写回阵型和视频资料库。

验收标准：

- 用户能查看一场战争的基础复盘信息。
- 用户能从复盘记录进入阵型详情。
- 关键阵型和视频能被标记并沉淀。
- 后续找阵结果可以引用历史表现。

主要风险：

- 复盘功能膨胀成完整分析平台。
- 攻击原因、失败原因难以自动判断。
- 历史数据来源不稳定。

风险控制：

- 先做记录展示和后台标记。
- 不做自动失败原因分析。
- 不做复杂评分模型。

不做事项：

- 不做完整统计分析系统。
- 不做 AI 复盘总结。
- 不做复杂图表大屏。

## 9. 跨阶段验收要求

每个阶段完成前必须检查：

- 是否符合 `mvp-scope.md`。
- 是否符合 `content-data-policy.md`。
- 是否有页面状态：加载、空、错误、低置信度、链接失效。
- 是否有对应数据模型或预留字段。
- 是否没有引入明确不做事项。

每个阶段完成后必须更新：

- `docs/project/documentation-status.md`
- 阶段验收记录。
- 后续阶段风险。

## 10. 推荐开发顺序

建议实际开发顺序：

1. 数据迁移和基础实体。
2. 内部后台骨架。
3. 阵型库列表和详情。
4. 官方战争 API。
5. 找阵上传任务。
6. 找阵结果页。
7. 视频和防守回放关联。
8. 后台审核与异常处理完善。
9. 复盘沉淀。

原因：

- 阵型库先行可以提供找阵结果页需要的基础资产。
- 内部后台先行可以承接自动化流程产出的低置信度和异常样本。
- 官方战争 API 与找阵上传并行推进，但找阵流程不能依赖战争数据才能运行。
- 视频关联在找阵结果页稳定后接入。

## 12. 验收标准

实施路线图文档视为完成时，需要满足：

- 覆盖 Phase 0 到 Phase 5。
- 每个阶段包含目标、交付物、核心能力、验收标准、主要风险和不做事项。
- 明确先做产品文档，再做基础数据和后台，再做战争 API 与找阵，再做视频，再做战争增强和复盘。
- 不引入超出 MVP 的登录、付费、完整 War Report、大规模视频帧索引、AI 打法推荐等能力。
