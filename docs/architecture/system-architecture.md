# WarSpark 系统架构设计

## 1. 文档目的

本文档定义 WarSpark 的系统级技术架构，用于约束后续功能技术设计、API 契约和实现拆分。本文档不定义具体接口字段，接口细节由 `docs/api/api-contract.md` 维护。

## 2. 架构目标

WarSpark MVP 的系统架构需要支撑：

- 截图上传和找阵任务状态流转。
- 轻量阵型库列表和详情。
- 阵型图片、阵型链接、视频时间戳、来源和审核状态管理。
- 相关攻击视频和防守回放展示。
- 首轮接入 CoC 官方 API 的战争上下文。
- 内部 admin API 和后端管理页面。
- 后续复盘和内容沉淀。

架构不追求首版复杂 AI 能力，不承诺大规模视频帧索引。战争数据进入首轮，但找阵流程仍必须能在官方 API 不可用时独立运行。

## 3. 系统边界

### 3.1 MVP 内部模块

| 模块 | 职责 |
| --- | --- |
| Layout Library | 阵型库列表、详情、图片、阵型链接、来源和状态。 |
| Image Search | 截图上传、自动校验、找阵任务、识别结果、候选匹配和状态流转。 |
| Video Reference | 相关攻击视频、防守回放、YouTube 时间戳和关联类型。 |
| Content Review | 来源记录、审核状态、质量状态、链接状态。 |
| War Data | CoC 官方 API、战争快照、成员、目标上下文。 |
| Admin Console | 内部 admin API、后端管理页面、审核、导入、异常样本处理。 |
| Storage | 图片对象存储、数据库持久化、临时文件管理。 |

### 3.2 后续模块

| 模块 | 职责 |
| --- | --- |
| Review Replay | 战后复盘、攻击记录、防守记录、资料沉淀。 |
| Advanced Operations | 批量导入增强、复杂审核流、失效链接批处理。 |

## 4. 推荐后端分层

当前项目基于 GinSpark 模板，后端建议维持清晰分层：

- HTTP Handler：负责请求解析、匿名上传限制、后台鉴权、响应包装。
- Service：负责业务流程编排和状态流转。
- Repository：负责数据库读写。
- External Client：负责 CoC 官方 API、YouTube 链接元信息等外部服务。
- Worker：负责异步找阵任务、链接检查、导入处理。
- Storage Adapter：负责图片上传、对象存储和临时文件。

模块之间不直接跨层调用数据库。Handler 不直接写数据库，Worker 不直接拼响应。

## 5. 核心数据流

### 5.1 截图找阵数据流

1. 用户上传截图。
2. HTTP Handler 校验文件格式、大小、尺寸和匿名上传频率。
3. Storage Adapter 保存原图或临时图。
4. Service 创建 `image_search_jobs`。
5. Worker 或同步处理器执行 EXIF 清理、图片归一、基础识别和候选匹配。
6. Service 写入 `image_search_results`。
7. 找阵结果页读取任务、候选阵型、视频关联和链接状态。
8. 可用阵型图片和阵型链接沉淀到 `base_layouts`、`layout_images`、`layout_links`。

### 5.2 阵型库数据流

1. 阵型由自动处理流水线、公开页面、授权导入、后台录入或找阵结果生成。
2. 阵型主记录写入 `base_layouts`。
3. 图片写入 `layout_images`。
4. 阵型链接写入 `layout_links`。
5. 列表页按 TH、类型、风格、来源、审核状态筛选。
6. 详情页聚合阵型、图片、链接、视频和防守记录。

### 5.3 视频关联数据流

1. 自动检查、后台维护或授权导入 YouTube 视频和时间戳。
2. 视频主记录写入 `videos`。
3. 阵型和视频的时间戳关联写入 `layout_video_matches`。
4. 找阵结果页按 `attack_video` 和 `defense_replay` 分组读取。
5. 视频失效时只更新状态，不删除历史关联。

### 5.4 战争数据数据流

1. 用户输入部落 tag 或玩家 tag。
2. External Client 调用 CoC 官方 API。
3. Service 缓存或写入 `war_snapshots`、`war_members`。
4. 用户选择敌方目标。
5. 找阵任务绑定目标上下文，但不依赖战争数据才能执行。

### 5.5 后台管理数据流

1. 自动处理流水线生成低置信度、冲突、失效或异常记录。
2. 内部管理员进入后端管理页面。
3. Admin API 读取阵型、图片、链接、视频时间戳、导入批次和找阵任务。
4. 管理员修正状态、隐藏内容、更新链接或补充来源。
5. 写操作记录到 `admin_audit_logs`。

## 6. 存储设计

### 6.1 数据库

数据库保存结构化业务数据：

- 阵型、图片、链接。
- 视频和视频关联。
- 找阵任务和结果。
- 战争快照和成员。
- 导入批次和后台审计日志。
- 来源、审核、质量和链接状态。

数据库不保存大体积原始图片二进制。

### 6.2 对象存储

对象存储保存：

- 用户上传截图。
- 阵型主图。
- 候选图和参考图。

对象存储记录必须在数据库中有引用。失效图片不能直接从页面静默失败，需要展示占位状态。

### 6.3 缓存

缓存用于：

- CoC 官方 API 响应。
- 阵型列表筛选结果。
- 热门 TH / 热门视频入口。
- 找阵任务短期状态轮询。

缓存不能作为唯一数据源。缓存丢失不应导致业务数据丢失。

## 7. 异步任务

建议使用 Worker 处理以下任务：

- 图片识别和候选匹配。
- 官方游戏打开链接和来源页面可用性检查。
- 视频链接可用性检查。
- 授权导入解析。
- 批量内容审核辅助任务。

MVP 可以先用同步或轻量 Worker 实现，但数据模型必须保留任务状态，避免后续改造时推翻页面流程。

## 8. 外部服务

### 8.1 Clash of Clans 官方 API

用途：

- 部落信息。
- 玩家信息。
- 当前战争和 CWL。

限制：

- 不作为 MVP 找阵硬依赖。
- 缓存时间需要遵守 API 实际限制。
- API 不可用时保留找阵流程。

### 8.2 YouTube

用途：

- 打开公开视频和时间戳。
- 保存视频 ID、标题、频道和时间戳。

限制：

- 不下载视频。
- 不自动抓取视频画面。
- 不承诺自动识别配兵或打法。

### 8.3 公开阵型页面和授权导入

用途：

- 获取候选阵型图片、阵型链接和视频时间戳。

限制：

- 不绕过登录、付费、私域权限。
- 所有导入数据必须记录来源和审核状态。

## 9. 错误处理

### 9.1 用户可见错误

| 场景 | 用户可见状态 |
| --- | --- |
| 文件格式不支持 | 上传失败，可重新选择。 |
| 文件过大 | 上传失败，提示更换或压缩。 |
| 图片尺寸过小 | 上传失败，提示更换更清晰截图。 |
| 匿名上传过于频繁 | 上传失败，提示稍后重试。 |
| 图片处理失败 | 找阵任务 `failed`，可重新上传。 |
| 低置信度 | 显示候选，但明确提示谨慎参考。 |
| 无结果 | 展示无结果页和替代入口。 |
| 阵型链接失效 | 禁用复制/打开动作。 |
| 视频不可访问 | 展示视频失效状态。 |
| CoC API 不可用 | 战争数据不可用，但找阵可继续。 |

### 9.2 系统内部错误

内部错误需要记录：

- 错误码。
- 错误信息。
- 关联任务 ID。
- 外部服务响应状态。
- 可重试标记。

## 10. 部署边界

MVP 推荐最小部署单元：

- 一个 Go API 服务。
- 一个内部管理页面。
- 一个数据库。
- 一个对象存储或本地兼容存储。
- 一个可选 Worker 进程。
- 一个可选 Redis 缓存。

如果早期资源有限，Worker 可以和 API 服务同进程运行，但代码边界仍按 Worker 任务设计。

## 11. 安全与合规边界

- 上传文件需要限制大小、类型和访问路径。
- 匿名上传只允许图片，限制为 jpg/jpeg/png/webp、单图最大 10MB、最小边长 512px、处理后最大边长 4096px。
- 上传图片需要去除 EXIF 元数据，原始上传图默认保留 7 天。
- 匿名上传需要基础 IP 限流：每分钟最多 5 次，每小时最多 50 次。
- 后台写操作必须鉴权，不允许匿名访问。
- 外部 URL 不允许直接作为服务器本地路径读取。
- 私有 Discord / Telegram 不进入默认采集路径。
- YouTube 不做视频下载。
- 公开页面内容必须保留来源。
- 链接和图片状态必须可追踪。

系统架构文档视为完成时，需要满足：

- 明确后端模块和分层职责。
- 明确截图找阵、阵型库、视频关联、战争数据的数据流。
- 明确数据库、对象存储、缓存和异步任务边界。
- 明确外部服务和禁止行为。
- 明确错误处理和部署边界。
