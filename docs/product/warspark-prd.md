# WarSpark 战前情报站产品设计文档

## 1. 背景与定位

WarSpark 的产品方向从单纯的“阵型图库”升级为“Clash of Clans 战前情报站”。用户在部落战、CWL、友谊战和复盘场景中，不只是需要一个可复制阵型链接，更需要快速判断：

- 当前对手是谁、什么 TH、战争状态如何。
- 敌方阵型是否有相似样本、是否能反查复制链接。
- 这个阵型是否有相关攻击视频或防守回放。
- 当前目标是否值得优先处理，视频证据是否足够。
- 战后哪些阵型防守强、哪些打法稳定，后续如何沉淀经验。

WarSpark 参考两类竞品能力：

- Base Drop / BurntBase：截图找阵、相似阵型匹配、相关攻击视频、YouTube 时间戳、OpenLayout。
- War Report：当前战争、CWL、玩家、部落、攻击次数、星数、摧毁率、历史表现等战争数据看板。

WarSpark 不做简单的竞品功能堆叠，而是围绕“战前侦察 -> 找阵匹配 -> 视频参考 -> 战后复盘 -> 资料沉淀”形成一条完整决策链。

## 2. 产品目标

WarSpark 的长期目标是成为 CoC 部落战玩家的作战情报工具。首版目标不是覆盖所有 CoC 工具功能，而是先把“截图找阵 + 战争上下文 + 视频证据”这条主线跑通。

核心产品目标：

- 将阵型截图转化为可检索的情报入口。
- 将当前战争数据和阵型匹配结果合并展示。
- 将相关攻击视频、防守回放、视频时间戳、复制阵型链接组织成可学习的参考结果。
- 将找阵过程中沉淀的阵型图片和 OpenLayout 链接转化为可浏览的阵型库资产。
- 为部落战指挥、普通玩家、多账号玩家提供战前和战后的决策依据。
- 为后续阵型库、视频库、复盘库、社区投稿打基础。

## 3. 目标用户

### 3.1 部落战指挥

关注整场战争的攻击分配、剩余攻击次数、敌我 TH 分布、风险阵型和三星机会。

典型需求：

- 快速查看当前战争整体状态。
- 找出敌方难打阵型。
- 为成员分配推荐目标。
- 复盘哪些阵型防守成功，哪些打法稳定。

### 3.2 普通参战玩家

关注自己要打的目标：这个阵有没有相关视频、被打出过什么结果、风险点在哪里。

典型需求：

- 上传目标截图找相似阵型。
- 查看真实攻击视频和时间戳。
- 通过视频自行学习打法。
- 复制或保存相似阵型。

### 3.3 多账号玩家

关注多个账号的当前战争任务、英雄状态、找阵结果和攻击进度。

典型需求：

- 快速切换玩家 tag。
- 查看每个账号还能打谁。
- 根据账号 TH 和目标位次筛选相关视频或相似阵型。

### 3.4 阵型与视频研究者

关注阵型、视频、攻击结果、防守表现之间的关联沉淀。

典型需求：

- 收集热门阵型。
- 维护视频时间戳和视频标签。
- 分析某类阵型被哪些攻击结果打穿。
- 总结版本 meta。

## 4. 产品主线

### 4.1 战争情报

用户输入部落 tag 或玩家 tag，WarSpark 读取并展示当前战争、CWL、玩家信息、TH 分布、攻击次数、星数、摧毁率等数据。

核心能力：

- 当前战争状态：准备日、战斗日、已结束、不可访问。
- 敌我双方：部落名称、等级、成员数量、总星数、总摧毁率。
- 成员列表：序号、玩家名、TH、攻击次数、被打情况、星数贡献。
- TH 分布：双方 TH 等级分布，用于判断匹配强度。
- 攻击进度：已用攻击、剩余攻击、最佳攻击结果。
- 战争风险提示：敌方高防守表现目标、我方未出手成员、低星攻击记录。

参考 War Report，但 WarSpark 的展示重点应服务于“下一步打谁、怎么打”，不是只做数据看板。

### 4.2 截图找阵

用户上传敌方阵型截图，WarSpark 识别 TH 和基础结构，匹配相似阵型、相关攻击视频、防守回放、OpenLayout。

核心能力：

- 上传阵型截图。
- 识别 TH 和可见建筑数量。
- 匹配相似阵型。
- 展示匹配可信度。
- 按“进攻视频”和“防守回放”分组结果。
- 提供 YouTube 时间戳和 OpenLayout。
- 未命中时展示相似阵型和同 TH 热门攻击视频。
- 不要求自动识别配兵、流派或完整打法，用户通过相关视频自行学习。

首版不承诺精确 AI 算法，可以先使用人工整理、半自动标注和候选匹配方式搭建可用流程。

### 4.3 复盘分析

战后复盘用于沉淀经验，不作为首版重点，但需要在数据结构和页面入口上预留。

核心能力：

- 查看本场战争攻击记录。
- 统计每个阵型的防守结果。
- 统计每种流派的星数和摧毁率表现。
- 标记值得收藏的阵型或打法。
- 生成部落战复盘摘要。

复盘分析最终应反哺截图找阵和视频参考：打过的阵、真实结果、失败原因都可以成为后续排序和筛选的依据。

### 4.4 阵型库 / 视频资料库

阵型库和视频库既是底层支撑，也是可以被用户直接使用的内容资产。找阵过程中发现的阵型图片、OpenLayout 链接、相关视频和防守结果，不应只留在内部数据表里，而应沉淀成可浏览、可筛选、可复用的阵型记录。

阵型库不是首页主线，首页仍优先服务“输入部落 tag / 上传截图”的作战入口。但当用户从找阵结果、战争目标或搜索入口进入时，阵型库需要提供完整的浏览和详情体验。

阵型库用于保存：

- 阵型图片。
- OpenLayout 链接。
- TH 等级。
- 阵型类型：War、CWL、Trophy、Farm、Legend、Anti 2、Anti 3 等。
- 风格标签：Ring、Box、Diamond、Island、Toxic、Progress 等。
- 关联视频和防守表现。
- 来源信息：找阵命中、公开页面、授权导入、人工录入。
- 质量状态：已审核、待审核、低置信度、链接失效。

视频库用于保存：

- YouTube 视频 ID 和时间戳。
- 视频标题、频道、发布时间。
- 攻击方、被攻击方、TH、星数、摧毁率。
- 视频标签。
- 关联阵型或相似阵型簇。

资料库的价值不只是“展示很多卡片”，而是让找阵结果可以被复用：一次命中的阵型，可以成为后续用户浏览、搜索、复制、对比和复盘的内容资产。

## 5. 核心用户流程

### 5.1 从战争进入找阵

1. 用户输入部落 tag。
2. 系统展示当前战争信息。
3. 用户点击敌方某个目标。
4. 系统进入目标情报页。
5. 用户上传该目标阵型截图。
6. 系统识别 TH 并匹配相似阵型。
7. 系统展示进攻视频、防守回放、复制链接。
8. 用户打开相关视频学习，或复制相似阵型链接。

### 5.2 从截图直接找阵

1. 用户打开找阵页。
2. 用户上传截图。
3. 系统识别 TH。
4. 系统返回相似阵型和结果分组。
5. 用户查看进攻视频、防守回放、OpenLayout。
6. 用户可补充部落 tag，将结果绑定到当前战争目标。

### 5.3 从找阵沉淀阵型库

1. 系统在找阵结果中识别到可用阵型图片和 OpenLayout。
2. 系统生成或关联一条阵型记录。
3. 阵型记录进入待审核或已审核状态。
4. 用户可以从找阵结果进入阵型详情页。
5. 后续用户可在阵型库中按 TH、类型、风格、来源、审核状态筛选该阵。

### 5.4 从复盘沉淀资料

1. 战争结束后，用户打开复盘页。
2. 系统展示攻击记录和防守记录。
3. 用户标记关键阵型和关键视频。
4. 系统将阵型、视频、结果沉淀到资料库。
5. 后续找阵时，这些记录参与排序和筛选。

## 6. 页面信息架构

### 6.1 首页 / 作战台

首页直接提供两个主入口：

- 输入部落 tag / 玩家 tag：进入战争情报。
- 上传阵型截图：进入截图找阵。

首页辅助展示：

- 最近查看的部落。
- 最近上传的找阵记录。
- 当前战争提醒。
- 热门 TH / 热门视频入口。

### 6.2 战争情报页

核心模块：

- 战争概览：双方部落、星数、摧毁率、状态、剩余时间。
- TH 分布：敌我 TH 对比。
- 敌方列表：序号、玩家、TH、被打情况、最佳防守结果、找阵按钮。
- 我方列表：玩家、TH、攻击次数、已打目标、剩余攻击。
- 风险提示：高价值目标、未出手成员、低星记录。

### 6.3 目标情报页

核心模块：

- 目标基础信息：敌方序号、玩家名、TH、当前被打情况。
- 阵型截图区：上传、替换、识别状态。
- 匹配结果摘要：TH、建筑检测数量、相似度、候选数量。
- 相关攻击视频：按匹配可信度排序。
- 防守回放：展示该阵或相似阵的防守表现。
- 操作区：打开视频、复制阵型、标记计划。

### 6.4 找阵结果页

核心模块：

- 检测信息：TH、截图质量、识别数量、是否需要重新裁剪。
- 匹配摘要：最佳匹配、相似阵型数量、可信度。
- 进攻视频：真实攻击视频、星数、摧毁率、视频标签、时间戳。
- 防守回放：防守视频、进攻结果、对手信息、时间戳。
- 复制链接：OpenLayout、官方复制链接、备用链接。
- 相似阵型：同 TH、同结构、同风格候选。
- 空状态：无精确匹配时展示相似阵型、同 TH 热门视频和手动提交入口。

### 6.5 复盘页

核心模块：

- 战争结果：胜负、星数、摧毁率、攻击效率。
- 攻击记录：谁打谁、几星、摧毁率、是否补星。
- 防守记录：哪个阵被打、被几星、对应视频或备注。
- 阵型表现：高防守阵型、低防守阵型。
- 攻击结果表现：三星率、平均摧毁率、失败样本。

### 6.6 阵型 / 视频资料库

核心模块：

- 阵型库列表：TH、类型、风格、来源、审核状态、更新时间、复制链接。
- 阵型详情：阵型图片、OpenLayout、来源、审核状态、关联视频、防守记录、相似阵型。
- 入库提示：从找阵结果沉淀的新阵型需要标记来源和置信度。
- 视频列表：TH、标签、星数、频道、时间戳。
- 视频详情：关联阵型、攻击结果。

## 7. 数据与内容边界

WarSpark 的数据来源需要分层处理：

- 官方 API：用于部落、玩家、当前战争、CWL 等结构化数据。
- 用户上传：用于截图找阵、手动复盘、资料补充。
- 公开页面：用于公开阵型链接和公开图片的候选采集。
- 授权导入：用于用户拥有权限的 Discord 导出、CSV、JSON、人工整理资料。
- 人工维护：用于高质量视频时间戳、阵型标签、视频标签。

默认不做：

- 私有 Discord / Telegram 抓取。
- 登录绕过、付费内容绕过。
- YouTube 视频下载或未授权批量抓取。
- 游戏客户端自动化或逆向。
- 对第三方站点数据的直接复制。

## 8. 首版 MVP 范围

MVP 聚焦“找阵核心 + 战争上下文预留”。

必须包含：

- 上传阵型截图。
- 展示识别 TH 和基础检测信息。
- 展示相似阵型候选。
- 结果按“进攻视频”和“防守回放”分组。
- 视频卡片支持 YouTube 时间戳。
- 支持展示 OpenLayout。
- 支持将命中的阵型图片和 OpenLayout 沉淀为基础阵型记录。
- 支持轻量阵型库列表和阵型详情页。
- 支持低可信度和无结果状态。
- 页面结构预留战争目标信息。

可以简化：

- 战争数据可以先做 tag 输入和基础展示，不要求完整复盘。
- 阵型匹配可以先用人工数据和候选相似度，不承诺精确 AI。
- 视频库可以先人工维护少量高质量样本。
- OpenLayout 可以先作为外部链接管理。
- 阵型库先只做基础筛选和详情展示，不做完整运营后台。

不纳入 MVP：

- 登录、收藏、会员、付费。
- 投稿审核后台。
- 移动 App。
- 完整 War Report 式多端工具。
- 完整 BurntBase 式大规模视频帧索引。
- 自动识别流派、配兵链接、打法推荐。
- 自动化 Discord 私域采集。
- 完整阵型图库运营后台。

## 9. 阶段规划

### 9.1 MVP：找阵情报页

目标：让用户上传截图后能获得可执行结果。

交付：

- 找阵页。
- 找阵结果页。
- 轻量阵型库列表页。
- 阵型详情页。
- 阵型 / 视频基础数据模型。
- 人工维护样本数据。
- 战争目标信息预留。

### 9.2 V1：战争数据接入

目标：让用户从当前战争进入找阵流程。

交付：

- 部落 tag / 玩家 tag 输入。
- 当前战争概览。
- TH 分布。
- 敌我成员列表。
- 敌方目标详情页。
- 从目标详情页进入截图找阵。

### 9.3 V2：复盘与资料沉淀

目标：让战后数据反哺后续推荐。

交付：

- 战争复盘页。
- 阵型防守表现统计。
- 攻击结果表现统计。
- 阵型 / 视频资料库完善。
- 人工审核与标注流程。

## 10. 竞品参考结论

### 10.1 Base Drop

参考价值：

- 截图找阵入口清晰。
- 结果按进攻和防守组织。
- YouTube 时间戳和 OpenLayout 接近用户真实动作；CopyArmy 可作为后续增强，不作为首版要求。

WarSpark 的处理：

- 借鉴功能结构，不复制品牌、文案或数据。
- 首版重点参考它的结果页组织方式。

### 10.2 BurntBase

参考价值：

- 明确证明“上传阵型截图找三星视频”有市场。
- 长期护城河在视频索引和匹配质量。

WarSpark 的处理：

- 作为长期能力对标。
- 首版不承诺同等规模的视频帧索引。

### 10.3 War Report

参考价值：

- 证明战争数据看板有稳定需求。
- 当前战争、CWL、玩家、部落、历史表现适合作为 WarSpark 的上游情报层。

WarSpark 的处理：

- 不复刻完整多端数据工具。
- 把战争数据服务于“选目标、找阵、看视频、复盘”。

### 10.4 ClashBaseLink / CocBases / ClashCodes

参考价值：

- 阵型分类、TH 筛选、复制链接、SEO 页面。

WarSpark 的处理：

- 作为阵型库列表、阵型详情、TH 筛选、复制链接体验的参考。
- 首屏不做传统图库首页，但阵型库作为找阵结果沉淀后的可浏览模块。

### 10.5 Blueprint / Clash Champs

参考价值：

- Pro base、付费阵型、专家内容、社区和赛事运营。

WarSpark 的处理：

- 作为后续商业化和社区化参考。
- 不进入首版范围。

## 11. 成功指标

MVP 阶段关注：

- 上传截图到结果页的完成率。
- 有结果搜索占比。
- 用户点击 YouTube 时间戳的比例。
- 用户复制 OpenLayout 的比例。
- 找阵结果沉淀为阵型记录的比例。
- 阵型详情页打开率。
- 阵型库筛选使用率。
- 低可信度结果的退出率。
- 用户是否愿意再次上传截图。

V1 阶段关注：

- tag 查询成功率。
- 从战争页进入目标详情页的比例。
- 从目标详情页进入找阵页的比例。
- 单场战争内的多次查询次数。

V2 阶段关注：

- 战后复盘打开率。
- 阵型和视频资料沉淀数量。
- 阵型库内容复用次数。
- 用户回访频率。

## 12. 待补充问题

- 首版是否优先做英文界面、中文界面，还是双语。
- 首批数据从哪些公开阵型站和人工视频样本开始。
- 官方 CoC API key 和数据缓存策略。
- 阵型图片和用户上传截图的存储策略。
- YouTube 视频时间戳的人工维护流程。
- 低可信度匹配结果的展示标准。
- 是否需要在首版加入用户反馈入口。
- 是否需要配兵链接、打法总结、AI 推荐，等用户反馈后再评估。
